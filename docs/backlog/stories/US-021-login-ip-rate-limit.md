# US-021 應用程式層的登入 IP 頻率限制

## User Story(使用者故事)
身為課外組承辦人（系統管理者），我想要系統本身限制同一來源 IP 在短時間內的登入嘗試次數，以便即使部署時沒有設定反向代理限流，也能降低大量猜測密碼、大量鎖住他人帳號，以及未登入者大量觸發密碼雜湊耗盡伺服器資源的風險。

## 背景
- 目前登入鎖定以**帳號**為鍵（US-013 AC3、ADR-005）：知道學號的人可故意輸錯密碼鎖住他人帳號（帳號鎖定型 DoS，ADR-005 已列為接受風險）。
- 未登入者可大量送出登入請求，每次都觸發 argon2 雜湊運算（CWE-400）；目前只以同時運算數上限緩解。
- 部署層建議由反向代理對 `POST /login` 做 IP 頻率限制（overview.md 第 7 節）；本 Story 是**應用程式層的補強**（縱深防禦），不取代反向代理設定。

## 驗收條件（Acceptance Criteria）
以下以預設值「每個 IP 每 60 秒最多 10 次登入請求」舉例，實際門檻可由 `.env` 設定（AC7）。

### AC1 超過頻率被拒絕
- Given 來源 IP `203.0.113.10` 在 60 秒內已送出 10 次 `POST /login`（不論成功或失敗、不論帳號為何）
- When 同一 IP 第 11 次送出登入（即使帳號密碼正確）
- Then 系統回應 **429**，顯示「嘗試次數過多，請稍後再試」，並帶 `Retry-After` 標頭；不登入、不建立 Session
- 且 訊息不透露帳號是否存在、是否被鎖定

### AC2 被限流的請求不耗用密碼雜湊、不計入帳號失敗次數
- Given 某 IP 已達頻率上限
- When 該 IP 再送出登入請求
- Then 系統在進行密碼雜湊驗證**之前**就拒絕；該請求**不計入**所填帳號的失敗次數（US-013 AC3），因此不會因此推進該帳號的鎖定

### AC3 時間窗過後恢復
- Given 某 IP 因 AC1 被限流
- When 時間窗結束後再以正確帳號密碼登入
- Then 依 US-013 正常流程處理，登入成功

### AC4 不同 IP 互不影響
- Given IP A 已達頻率上限
- When IP B 送出登入
- Then IP B 依正常流程處理，不受 IP A 影響

### AC5 無法以偽造標頭繞過
- Given 系統未設定可信任的反向代理
- When 攻擊者在每次請求帶入不同的 `X-Forwarded-For` 值
- Then 系統以實際連線 IP 計數，仍在第 11 次被拒絕
- 且 有設定可信任代理時，只採用該代理轉送的來源 IP（設定方式與 overview.md 第 7 節一致，不信任任意來源的轉送標頭）

### AC6 併發請求不超過上限
- Given 同一 IP 同時送出 30 個登入請求
- When 這些請求併發處理
- Then 通過頻率檢查、實際進入密碼驗證的請求不超過 10 個（需有併發測試）

### AC7 門檻可設定且有範圍驗證
- Given `.env` 設定每 IP 的次數上限與時間窗
- When 系統啟動
- Then 依設定生效；設定值超出合理範圍（例如 0 或負數）時拒絕啟動；`.env.example` 同步新增範例值

### AC8 安全日誌
- Given 某 IP 觸發頻率限制
- When 請求被拒絕
- Then 記錄頻率限制的安全事件（含來源 IP 與時間窗資訊；不記錄密碼、Token，也不記錄被限流請求所填的帳號）；同一 IP 在同一時間窗只記錄一次，避免日誌洪水

### AC9 不影響其他頁面
- Given 某 IP 已達登入頻率上限
- When 該 IP 開啟公開頁面（例如場地借用狀況）或 `GET /login`
- Then 正常回應；頻率限制只套用在 `POST /login`

## 商業規則與限制
- 只限制 `POST /login`；其他 route 的頻率限制不在本 Story 範圍。
- 校園網路可能有多人共用同一個對外 IP（NAT），門檻需足以容納正常登入尖峰（見待釐清）。
- 與 US-013 帳號鎖定並存：IP 限制先檢查，通過後才進入帳號鎖定與密碼驗證。

## 假設
- 頻率計數的儲存方式（資料庫或記憶體）與多 worker 下的一致性由 System Analyst 設計並記錄 ADR；AC6 的併發保證需在選定的部署方式下成立。
- 依 overview.md 第 9 節原則，優先不新增 Rate limit 套件；若 SA 評估需要新增，需經 Security Reviewer 同意並通過 `pip_audit`。

## 待釐清（未解決前 DoR 不完整）
1. **校園 NAT 門檻**：淡江校園網路或宿舍是否多人共用對外 IP？預設「每 IP 每 60 秒 10 次」是否會在選課、活動申請尖峰誤擋正常使用者？需課外組／資訊處確認，或由 SA 評估以較寬鬆的預設值上線。
2. **針對單一帳號的鎖定 DoS**：IP 頻率限制只能減緩「大量帳號」被鎖，無法阻止攻擊者在 15 分鐘內以 5 次嘗試鎖住**特定**帳號（5 次低於 IP 門檻）。是否需要調整鎖定策略（例如改以「帳號＋IP」為鍵、或鎖定改為漸進延遲）？此為設計取捨，需 System Analyst 與 Security Reviewer 評估後由主對話決定；目前不納入本 Story 範圍。
3. 未通過 CSRF 檢查的 `POST /login`（403）是否也計入 IP 次數？建議由 SA 於設計時決定並寫入 ADR。

## 資安考量
- 對應：CWE-307（過多認證嘗試）、CWE-400（資源耗用）、OWASP ASVS 5.0 V6（Level 2）。
- 權限：公開端點；限流不得洩漏帳號存在與否（CWE-204）。
- 輸入驗證：來源 IP 只取自實際連線或明確設定的可信任代理（防 `X-Forwarded-For` 偽造）。
- 併發：計數「檢查＋遞增」需原子化，避免 TOCTOU（與 ADR-005 同樣的問題）。
- 日誌：避免攻擊時日誌洪水；不記錄密碼與 Token。
- 必須有負面測試：超過門檻被拒、偽造標頭無法繞過、併發不超過上限。
